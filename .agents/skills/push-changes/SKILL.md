# Перед кожним push

Залишай зміни локально. Виконуй `git push` лише на окреме явне прохання користувача. Попередній дозвіл відкрити або оновити PR не означає дозволу пушити кожну наступну правку.

Перед кожним push у будь-яку віддалену гілку запусти локально й дочекайся успішного завершення всіх перевірок:

1. `npm run format:check`.
2. `npm test` — включає перевірку типів, збірку, модульні й архітектурні тести.
3. `npm run test:browser` — включає збірку та браузерні тести.
4. `git diff --check` і `git diff --cached --check` — пробіли та маркери конфліктів.

Перевіряй остаточні зміни, які підуть у push. Не покладайся на результати попереднього push або віддаленого CI. Якщо після перевірок змінилися файли, повтори перевірки перед push.

Якщо хоча б одна перевірка впала, не запустилася або не завершилася, не виконуй push. Не обходь помилку й не вимикай перевірку. Дай користувачу короткий підсумок за скілом [ukrainian-language](../ukrainian-language/SKILL.md): що не пройшло, відома причина або що ще треба з’ясувати, наступний крок. Явно зазнач: «Зміни не запушено».

Автоматичні перевірки й публікація запускаються лише після push у `main`. Вони не замінюють локальні перевірки перед push.

## Підсумок користувачу

Після виконання дай підсумок за [ukrainian-language](../ukrainian-language/SKILL.md) у форматі нижче. Підстав фактичні дані поточного запуску; не залишай поля в фігурних дужках і не копіюй результати попередніх запусків. Довгі логи заміни коротким поясненням; за потреби додай посилання на файл журналу.

У таблиці використовуй `✓` для успішної перевірки, `✗` для помилки, `— Не запускалась` або `— Не завершилась` для решти. Для тестів додавай фактичні кількості успішних, невдалих і пропущених тестів, якщо вони є у звіті. «Типи та збірка» успішні лише тоді, коли всі їхні запуски завершилися успішно. Пробіли та маркери конфліктів — технічна перевірка Git, а не рев’ю логіки коду.

### Успішний push

Повідомляй про успіх лише після підтвердження push. Якщо PR немає, замість посилання вкажи remote і гілку. Стан робочої папки звір із `git status --short`.

```markdown
**✓ Зміни запушено**

[PR #{номер}]({адреса PR}) · коміт `{короткий SHA}`
Зміна: {одне речення про результат}.

| Локальні перевірки | Результат |
|---|---|
| Форматування | ✓ |
| Типи та збірка | ✓ |
| Модульні тести | ✓ {пройшло}/{усього} |
| Браузерні тести | ✓ {пройшло}/{усього} |
| Пробіли та маркери конфліктів | ✓ |

{Робоча папка чиста або короткий опис залишених локальних змін.}
```

### Перевірка або push не вдалися

Вкажи відому причину, а якщо її ще не встановлено — скажи це прямо. Не підмінюй помилку доступу чи запуску повідомленням про невдалий тест. Якщо всі перевірки пройшли, але сам push завершився помилкою, залиш їхні успішні результати в таблиці та поясни помилку push. Якщо результат push невідомий через обрив зв’язку, спершу перевір віддалену гілку; без підтвердження напиши «Результат push не підтверджено».

```markdown
**✗ Зміни не запушено**

| Локальні перевірки | Результат |
|---|---|
| Форматування | {статус} |
| Типи та збірка | {статус} |
| Модульні тести | {статус і кількість} |
| Браузерні тести | {статус і кількість} |
| Пробіли та маркери конфліктів | {статус} |

**Проблема:** {що не пройшло та відома причина або що ще треба з’ясувати}.
**Наступний крок:** {конкретна дія для усунення проблеми}.

Зміни залишилися локально.
```
